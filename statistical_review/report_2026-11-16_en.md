# Review of the equivalence tests, the clustering and the bootstrap procedures

*Report received by the author on 16 November 2026. English translation of the Italian original (`report_2026-11-16_it.md`), translated by the author with AI assistance; tables and numbers unchanged. Author of the report: an independent professional statistician, paid by the author for the review, who asked to remain anonymous.*

## Preliminary note

The material available in the replication repository of the study *Does SQALE Debt Explain Issue Effort Beyond Code Size?* was reviewed, with particular attention to the equivalence tests of hypotheses H1, H2 and H3, to the Holm correction and to the effect of the clustering structure on the results.

The aim was to understand whether the conclusions of the study are supported by the statistical analyses reported in the package and, above all, whether they remain valid when the way in which the dependence between issues is estimated is changed.

This review covered the scripts, protocols and results already distributed in the repository. A new independent run of the whole pipeline on the original data has not yet been completed. The values reported below therefore correspond to the results in the replication package.

## 1. Equivalence tests of hypotheses H1 and H2

The first two hypotheses concern the relationship between technical debt measured with SQALE and the hours logged on Jira issues, accounting for code size.

H1 considers the technical debt in the modified files, while H2 considers the debt associated with the lines of code actually affected by the change.

The protocol states that a Spearman partial correlation below 0.10 in absolute value can be considered negligible in practice. This condition is checked with 90% confidence intervals and an equivalence test.

The available results are:

| Hypothesis | Moodle | MariaDB |
|---|---:|---:|
| H1 – Partial correlation | −0.0244 | 0.0234 |
| H1 – 90% CI | [−0.0946; 0.0263] | [−0.0375; 0.0839] |
| H2 – Partial correlation | −0.0040 | −0.0084 |
| H2 – 90% CI | [−0.0657; 0.0627] | [−0.0852; 0.0528] |

In all four cases the confidence intervals lie within the equivalence margin set by the protocol, ±0.10. Applying the planned criterion, the results indicate that, in the analysed sample and with the developer bootstrap, there is no relationship of relevant size between SQALE debt and logged hours once code size is controlled for.

This result does not mean that technical debt has no relationship with effort. More precisely, it indicates that under the conditions considered the study does not detect an additional contribution of practical size beyond what code size already explains.

## 2. Holm correction

The Holm procedure is applied to the four one-sided tests for a positive correlation: H1 and H2, each in Moodle and MariaDB.

The values reported in the repository are:

| Test | Original p-value | Holm-adjusted p-value |
|---|---:|---:|
| MariaDB H1 | 0.2558 | 1.0000 |
| Moodle H2 | 0.5548 | 1.0000 |
| MariaDB H2 | 0.5796 | 1.0000 |
| Moodle H1 | 0.7944 | 1.0000 |

After the correction, none of the four tests gives statistical evidence for a positive correlation.

It is important to distinguish this result from the equivalence check. The Holm correction concerns the one-sided tests for a positive correlation; the equivalence judgement comes from comparing the confidence intervals with the ±0.10 margin. The two procedures have different purposes, and the results of one should not be used in place of the other.

## 3. Effect of the clustering structure

The most delicate part of the review concerns how the dependence between issues is handled.

In the main analysis the bootstrap clusters issues by developer. This accounts for the fact that several issues may have been handled by the same person. However, issues assigned to different developers can touch the same software components. In that case dependence through developers alone may not represent the structure of the data.

To examine this, the repository contains an additional analysis that considers developer and first Jira component of the issue together.

The H1 results change substantially:

| Project | Partial correlation | 90% CI with two-way clustering |
|---|---:|---:|
| Moodle | −0.0244 | [−0.1476; 0.0722] |
| MariaDB | 0.0234 | [−0.0855; 0.1345] |

In both projects the intervals are no longer entirely between −0.10 and +0.10. The result is therefore inconclusive with respect to the equivalence criterion.

A further check uses developer and component fixed effects. Here too the intervals do not allow equivalence to be confirmed:

- Moodle: partial correlation −0.0444, 90% CI [−0.1116; 0.0299].
- MariaDB: partial correlation 0.0351, 90% CI [−0.0172; 0.1054].

These results suggest that the H1 conclusion depends on how the structure of the data is modelled. With developer clustering equivalence is confirmed; when the component is also considered, the intervals become wider and no longer exclude effects of potentially relevant size.

The issue deserves attention because the code of one component can be changed by several developers and touched by many issues. Observations are therefore not necessarily independent even when they come from different people.

## 4. Checks on the bootstrap and simulations

The repository also contains simulations that assess how often the two-way bootstrap gives an inconclusive result when the correlation has a known size.

The simulations used 200 experiments and 1,000 bootstrap replicates per experiment.

For Moodle, when the true correlation is set to zero, 92% of the simulations give an inconclusive result; equivalence is declared in only 8% of cases. When the correlation is set to 0.10, 66.5% of the results indicate a positive correlation of uncertain size and the remaining 33.5% are inconclusive.

For MariaDB, with a true correlation of zero, 87% of the simulations are inconclusive and 13% give equivalence. With a correlation of 0.10, 44.5% indicate a positive correlation of uncertain size and 55% are inconclusive.

These data show that two-way clustering makes it harder to obtain intervals precise enough to confirm equivalence. Consequently, an inconclusive result should not be read as evidence that a relationship exists, but as an inability to determine its size with enough precision.

The simulations thus reinforce a caution already seen in the real data: the equivalence conclusion also depends on the dependence structure assumed in the statistical model.

## 5. Check of hypothesis H3

H3 concerns the predictive value of SQALE. It compares a model that uses code size with a second model that also adds the technical debt measure.

The difference between the two models is assessed through the change in MAE. A negative value means the model with SQALE is better; a positive value means it is worse.

The reported results are:

| Project | MAE difference | 90% CI |
|---|---:|---:|
| Moodle | +0.0009 hours | [−0.00135; 0.00303] |
| MariaDB | −0.0194 hours | [−0.0558; 0.0166] |

The protocol considers relevant a change in MAE of at least 2% of the model based only on lines of code.

Both observed intervals lie within the equivalence margin. Adding the SQALE measure therefore does not give a predictive improvement of relevant size in the two projects examined.

Unlike H1, the H3 result stays stable in the additional checks reported in the repository. This makes the conclusion about the predictive contribution of SQALE more solid than the one about the correlation between debt and effort.

## 6. Concluding remarks

The review of the replication package confirms that the main results obtained with the developer bootstrap are consistent with the equivalence criteria set in the preregistration. For H1 and H2, in both projects, the confidence intervals lie within the ±0.10 margin. H3 also meets the equivalence criterion, indicating that adding SQALE does not appreciably improve the prediction of working hours compared with a model based on code size.

The clustering check, however, introduces an important limitation. When dependence between issues of the same component is also considered, the H1 result becomes inconclusive for both Moodle and MariaDB. It therefore cannot be stated that equivalence is independent of how observations are grouped.

The Holm correction shows no statistically significant positive correlation in the four tests considered. This is consistent with the absence of evidence for hypotheses H1 and H2, but it does not resolve the sensitivity of the intervals to clustering.

Overall, the results suggest that SQALE does not give a relevant predictive contribution beyond code size, at least under the conditions analysed. The conclusion about the relationship between technical debt and effort should, however, be stated more cautiously: the equivalence observed with the developer bootstrap does not hold when dependence between components is also considered.

For a definitive check, a new independent run of the scripts on the distributed data should be completed, checking in particular the two-way bootstrap, the reproducibility of the results and the sensitivity of the conclusions to different clustering structures. Until then, the results discussed here should be regarded as a review of the published replication material and not as a full computational reproduction of the study.
